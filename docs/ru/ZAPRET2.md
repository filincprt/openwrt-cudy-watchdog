- Служба: `/etc/init.d/zapret2`; состояние проверялось через `ubus call service list '{"name":"zapret2"}'` — `running=true`, PID `4164`, PID-file `/var/run/nfqws2_1.pid`.
- Проверка `pidof nfqws2` один раз вернула пусто, хотя procd/ubus одновременно показывал процесс работающим. Для состояния службы в этом случае использовать `ubus call service list '{"name":"zapret2"}'` и `ps w`, а не делать вывод только по `pidof`.
- Основные значения `/opt/zapret2/config`: `NFQWS2_ENABLE=1`, `MODE_FILTER=hostlist`, `NFQWS2_PORTS_TCP=80,443`, `NFQWS2_PORTS_UDP=443`, `DESYNC_MARK=0x40000000`, `FLOWOFFLOAD=donttouch`, `DISABLE_IPV6=1`. `FILTER_MARK` не был задан при прочтении конфигурации.
- IPv6-поддержка zapret2 при установке оставлена выключенной. В проверенной таблице правила очереди были для IPv4.
- Отдельной официальной страницы LuCI у этой установки нет; это ожидаемо для штатного shell/procd-инсталлятора. Управление службой доступно через init script/SSH; не ставить случайный LuCI-пакет только ради появления пункта меню.

## Активные стратегии и списки

Фактическая командная строка запущенного `nfqws2`:

- TCP 80 / HTTP: `fake:blob=fake_default_http:tcp_md5` + `multisplit:pos=method+2`.
- TCP 443 / TLS: `fake:blob=fake_default_tls:tcp_md5:tcp_seq=-10000` + `multidisorder:pos=1,midsld`.
- UDP 443 / QUIC: `fake:blob=fake_default_quic:repeats=6`.
- Для каждого профиля используются пользовательский список `/opt/zapret2/ipset/zapret-hosts-user.txt`, загруженный `/opt/zapret2/ipset/zapret-hosts.txt.gz` и исключения `/opt/zapret2/ipset/zapret-hosts-user-exclude.txt`.
- Автоматическое скачивание доменных списков включено в конфиге установщика и был успешно выполнен вручную `sh /opt/zapret2/ipset/get_antizapret_domains.sh`: exit code 0; архив проверен `gzip -t`; в распакованном списке было 130898 строк.
- Первая загрузка во время установки закончилась curl timeout, после чего `gunzip: invalid magic`. Это была невалидная/неполная загрузка; последующая ручная загрузка и запуск штатного скрипта прошли успешно.
- Установщик сообщил, что добавил cron-запись для автоматического обновления списка, но фактическое расписание ещё нужно проверить через `crontab -l`. Автообновление списка **не означает**, что стратегии или бинарник обновляются автоматически.
- Стратегии заданы явно в `NFQWS2_OPT`. Хотя `zapret-auto.lua` подключён как библиотека, в активной командной строке нет вызовов оркестратора/автоматического переключения стратегии. Не утверждать, что запущен авто-подбор стратегий.

## Проверенное применение nftables

- Таблицы одновременно присутствуют: `inet fw4`, `inet passwall2`, `inet zapret2`. zapret2 использует собственную таблицу, а не таблицу PassWall2.
- Активные правила zapret2 направляют первые пакеты TCP 80/443 и UDP 443 в NFQUEUE `300` (в обе стороны по заданным packet ranges). В обычном запросе YouTube/Discord пользователь подтвердил, что сайты работают на ПК и телефоне.
- Рабочие правила — это положительное доказательство того, что firewall конфигурирован; оно не доказывает, что каждый профиль нужен или оптимален.
- В `/opt/zapret2/init.d/openwrt/custom.d/40-passwall2-xray-exclude.sh` добавлен пользовательский hook. Он ставит бит `0x01000000` в conntrack mark для трафика с `meta mark & 0x000000ff == 0x000000ff` (PassWall2/Xray outbound), затем возвращает такие соединения до цепочки zapret2; для ответов стоит аналогичное исключение. В активных цепочках эти правила были видны после применения.
- PassWall2 использует mark `0x50535732` для TProxy/routing; в Xray outbound на стороне PassWall2 используется low byte `0xff` (`mark=255`). Это отличающиеся метки.
- **Ограничение:** новые правила не содержат счётчиков, поэтому число совпадений не измерялось. Сохранение после полного firewall restart/reboot ещё не подтверждено. Перед чисткой не удалять активный hook.
- Изменения касались только zapret2/firewall custom hook. PassWall2-узлы, Shunt и watchdog Auto не перенастраивались.

## PassWall2 — не путать с zapret2

- Наблюдались `passwall2.rulenode.protocol='_shunt'`, `shunt_group='RU'`, `Russia='_direct'`, `default_node='fAk268mE'`.
- Пользователь явно сообщал, что режим Auto работает нормально и в одном из моментов вручную выбирал резервный режим. Текущее `ha_watchdog.main.mode` не перечитывалось в последнем снимке; перед любыми операциями с маршрутизацией нужно проверить значение, не предполагать, что выбран Auto или Backup.
- Не включать штатную балансировку PassWall2 и не менять режим/узлы ради отладки zapret2 без отдельной просьбы.
- Цель разграничения: прямой Shunt-трафик может обрабатываться zapret2 по hostlist; внешний транспорт Xray/VLESS не должен повторно проходить desync. Правила добавлены, но счётчиками/перезапуском firewall и полным reboot ещё не подтверждены.

## Резервные копии и очистка

- Во время добавления custom hook копировались `/opt/zapret2/config` в файл вида `/root/zapret2-config-before-split-<timestamp>` и каталог `/opt/zapret2/init.d/openwrt/custom.d` в `/root/zapret2-custom-before-split-<timestamp>`. Точное имя/существование копий нужно проверить перед удалением.
- На роутере раньше было много версий `/usr/bin/passwall2-failover*` с суффиксами `.bak-before-...`. Их нельзя удалять вслепую: сначала составить inventory (имя, дата, размер), определить текущие active files и проверить, какая резервная копия предшествует последнему исправлению.
- Предпочтительная очистка: инвентаризировать, оставить минимум одну проверенную копию перед последними изменениями для каждого изменённого скрипта, упаковать старые варианты в проверенный архив и только потом удалить дубликаты. Не удалять активные скрипты, пользовательский hook, `/opt/zapret2/config`, бинарники, hostlist и списки исключений.
- Не запускать `rm` до просмотра списка кандидатов и явного подтверждения того, что путь относится к старой резервной копии, а не рабочему файлу.
