## Поля телеметрии и их сохранность

Секция UCI: `ha_watchdog_metrics.nodes`.

- `primary_result` / `backup_result` — сырой результат HTTP и время либо `no-response`.
- `primary_ok` / `backup_ok` — `online` или `offline`.
- `primary_rtt_ms` / `backup_rtt_ms` — задержка в округлённых миллисекундах либо `unknown`.
- `primary_failures` / `backup_failures` — число последовательных ошибок.
- `primary_checked_at`, `backup_checked_at`, `last_check` — локальное время роутера.
- `primary_summary` / `backup_summary` — строки для отображения в Home Assistant.

Публикатор сначала выполняет `uci revert ha_watchdog_metrics`, затем заново устанавливает полный набор свежих значений. Это не даёт разрастаться файлу отложенных изменений `/tmp/.uci/ha_watchdog_metrics`: ранее он достигал 48,8 КБ из-за накопления записей; после исправления наблюдался размер 722 байта. Метрики не коммитятся во flash при каждом обновлении. После перезагрузки они возвращаются к значениям по умолчанию до следующей публикации.

## Разделение проверок и публикации

В автоматическом режиме ядро проверяет оба узла на каждом полном цикле, но вызывает `passwall2-watchdog-publish-due`, который должен обновлять значения UCI примерно раз в случайные 180–300 секунд. В ручных режимах оболочка сразу закрепляет выбранный маршрут, а цикл отдельно запускает только проверку метрик с интервалом 180–300 секунд.

**Ещё требуется подтвердить в работе:** сравнить обычные строки проверок в логе, `metrics_last_publish`, `metrics_interval` и `last_check` хотя бы на протяжении двух циклов. Синтаксическая проверка сама по себе не доказывает работу таймера.

- HTTP 204 означает только то, что конкретный тестовый запрос прошёл через узел в данный момент. Это не гарантирует работу всех сайтов и не устанавливает причину отдельных сбоев.

- Причина прежних пустых результатов проверки не установлена.
- Служба запускалась после перезагрузки; но сценарий «основной узел недоступен → резервный → восстановление основного» ещё предстоит проверить безопасно, сохраняя локальный доступ.
